## 2026-05-13 - [style_registry.js Cache Optimization]
**Learning:** The style registry was repeatedly calling synchronous I/O (`localStorage.getItem`) and expensive parsing (`JSON.parse`) on every element style application, creating a severe bottleneck during dense page renders. Memory caching for static/rarely-changing global configurations is highly effective, but cross-tab synchronization must be handled manually via the `storage` event to prevent stale states in multi-window environments.
**Action:** When implementing global configuration managers, always use an in-memory cache variable backed by `localStorage` rather than querying `localStorage` continuously. Ensure cache invalidation logic is robust (both local updates and cross-tab `storage` events).

## 2026-05-14 - [dom_packer.js Configuration Reading Optimization]
**Learning:** Functions like `noMidLineSplitsEnabled` and `noMidParagraphSoftEnabled` in the hot rendering loop query `localStorage` directly via `localStorage.getItem("ravtext.spacing.v1")` and perform `JSON.parse` synchronously on every call during page layout. This is a massive layout engine bottleneck in `dom_packer.js` as these methods are evaluated repeatedly (sometimes thousands of times per page layout). This repeats the same anti-pattern found in `style_registry.js`.
**Action:** Configuration readings like `localStorage.getItem("ravtext.spacing.v1")` used in tight rendering loops must be cached into an in-memory variable (e.g. at module level or layout context level) rather than hitting synchronous I/O and JSON parsing dynamically upon layout calculation.
